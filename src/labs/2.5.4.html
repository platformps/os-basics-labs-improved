About this lab

In this lab you look at how Linux organizes drives and filesystems, connect a second drive to the folder tree, control who can read and change files, and compare the two kinds of links Linux supports.

Objectives

  • Part 1: Exploring filesystems in Linux
  • Part 2: File permissions
  • Part 3: Symbolic links and other special file types

This simulation stands in for the Security Workstation virtual machine. You are logged in as analyst; the sudo password is cyberops. Open Terminal from the Applications button to begin.

Part 1: Exploring filesystems in Linux

Linux supports many filesystem types. This lab focuses on the ext family, one of the most common on Linux.

Step 1: Access the command line

  1. Open Terminal from the Applications button.

Step 2: Display the filesystems currently mounted

A filesystem must be mounted before you can use it. Mounting links a partition on a drive to a folder, called the mount point. Everything on that partition then appears inside that folder.

  1. Run lsblk to list all block devices (drives and partitions). The Table view lists each device on its own row.

The workstation has three block devices: sda, sdb, and sr0 (a CD or DVD drive). Linux names hard drives /dev/sda, /dev/sdb, and so on, and adds a number for each partition, so sda1 is the first partition on sda. sda is a 10 GB disk and sdb is a 1 GB disk, each with one partition. USB flash drives often show up as /dev/sdX too.

  1. Run mount with no options to see detailed information about every mounted filesystem. Most of them are special system filesystems you can ignore for now.
  2. Focus on the root filesystem, stored on /dev/sda1. Send the output of mount to grep so only that line shows: run mount | grep sda1.

Which folder is /dev/sda1 mounted on, and what type of filesystem is it?

It is mounted on / (the root directory) and it is an ext4 filesystem.

  1. Run cd / and then ls -l.

What does this listing show? Where are the listed files physically stored?

It shows the contents of the root directory, the top of the whole folder tree. Because /dev/sda1 is mounted on /, these files are physically stored on the /dev/sda1 partition.

Why does /dev/sdb1 not appear in the mount | grep sda1 output, or in the mount output at all?

/dev/sdb1 is not mounted yet. (It would not match "sda1" either, but it is missing from the full mount list because it is not mounted.)

Step 3: Mount and unmount a filesystem manually

  1. Run cd ~ and ls -l. Check that the folder second_drive exists. (If it does not, create it with mkdir second_drive.)
  2. Run ls -l second_drive/. The folder is empty.
  3. Mount the second drive on it. The syntax is mount [options] device mount_point. Run sudo mount /dev/sdb1 ~/second_drive/. No output means it worked.
  4. Run ls -l second_drive/ again.

Why is the folder no longer empty? Where are the listed files physically stored?

After mounting, /home/analyst/second_drive is the entry point to the filesystem on /dev/sdb1. The files are stored on the second drive, not on sda1.

  1. Run mount | grep /dev/sd to see both drives.
  2. Unmount the drive. Make sure no terminal is inside the mount point, then run sudo umount /dev/sdb1. Run ls -l second_drive/ again; it is empty.

Part 2: File permissions

Every file and folder has an owner, a group, and three sets of permissions: for the owner (user), for members of the group, and for everyone else (others). Each set can allow read (r), write (w), and execute (x).

Step 1: View and change file permissions

  1. Run cd lab.support.files/scripts/ and then ls -l.

Who owns the file cyops.mn, and which group does it belong to?

The owner is analyst and the group is analyst.

The permissions of cyops.mn are -rw-r--r--. What does that mean?

The first character, -, means a regular file. The owner (analyst) can read and write it (rw-). Members of the analyst group can only read it (r--). Everyone else can also only read it (r--). Nobody can execute it.

  1. Run touch /mnt/myNewFile.txt. touch creates an empty file.
  2. Run ls -ld /mnt. The -d option shows the folder itself instead of its contents.

Why was the file not created?

/mnt is owned by root with permissions drwxr-xr-x. Only the owner, root, can write in it; analyst falls under "others," which can only read and enter it.

What could you do so the touch command works?

Run it as root with sudo, or change the permissions (or owner) of /mnt so analyst can write there.

  1. Mount the second drive again: sudo mount /dev/sdb1 ~/second_drive/. Then run cd ~/second_drive and ls -l.

What are the permissions of myFile.txt?

-rw-r--r--

chmod changes permissions. One common way is three octal digits, one each for owner, group, and others. Each digit adds read (4), write (2), and execute (1). So 6 is read and write (110 in binary, rw-), 5 is read and execute (101, r-x), and 7 is all three (111, rwx).

  1. Run sudo chmod 665 myFile.txt, then ls -l.

Did the permissions change? What are they now?

Yes: -rw-rw-r-x. The owner and group can read and write, and others can read and execute.

What command would give every user full access to myFile.txt (rwxrwxrwx)?

sudo chmod 777 myFile.txt

chown changes the owner. myFile.txt belongs to root, so analyst cannot change it yet.

  1. Make analyst the owner: run sudo chown analyst myFile.txt, then ls -l. (To change the owner and group together, use sudo chown analyst:analyst myFile.txt.)
  2. Now that analyst owns it, append a word without sudo: run echo test >> myFile.txt, then cat myFile.txt.

Did that work? Explain.

Yes. analyst now owns the file, and the owner's permissions (rw-) allow writing. The group (root) can also write, because the permissions are still 665.

Step 2: Directories and permissions

Folders have the same nine permission bits. There are also three special bits (setuid, setgid, and sticky), which are beyond this lab.

  1. Run cd ~/lab.support.files/ and ls -l.

Compare the lines for the malware folder and the mininet_services file. What is different at the start of each line?

The malware line starts with d, which marks a directory; mininet_services starts with -, a regular file.

The execute bit means something different for a folder. On a file, x lets the system run it as a program. On a folder, x lets a user enter the folder and reach the files inside it. chmod and chown work on folders the same way they work on files.

Part 3: Symbolic links and other special file types

The first character of each ls -l line shows the file type:

  • - regular file: text files, programs, images, compressed files
  • d directory (folder)
  • b block device: hardware that stores data in blocks, such as a drive
  • c character device: hardware that sends and receives a stream of characters, such as a terminal
  • p pipe (FIFO): passes data in first in, first out order
  • l symbolic link: points to another file or folder by its name
  • s socket: lets programs on the same computer communicate

Step 1: Examine file types

  1. Run cd ~ and ls -l. Each line starts with - for a file or d for a folder.
  2. Run ls -l /dev/. Find the block devices (b), character devices (c), and symbolic links (l).

Step 2: Symbolic and hard links

A symbolic link is like a shortcut: it points to another file's name. A hard link is a second name for the same file data (the same inode on the disk).

  1. Create two files: run echo "symbolic" > file1.txt and echo "hard" > file2.txt.
  2. Run ln -s file1.txt file1symbolic to create a symbolic link, and ln file2.txt file2hard to create a hard link.
  3. Run ls -l and look at the four files.

How can you tell the two kinds of links apart in the listing?

file1symbolic starts with l and shows -> file1.txt. file2hard looks like an ordinary file, and both file2hard and file2.txt show 2 in the second column, the link count: two names point to the same data. For a folder, the link count is 2 plus the number of folders inside it.

  1. Rename the originals: run mv file1.txt file1new.txt and mv file2.txt file2new.txt.
  2. Run cat file1symbolic and cat file2hard.

Why does one link still work and the other not?

file1symbolic points to the name file1.txt, which no longer exists, so it is a broken link. file2hard points to the file's data (its inode), not its name, so it still works after the rename.

What would happen to file2hard if you changed the text in file2new.txt?

file2hard would show the same change, because both names point to the same data on the disk.

Reflection

File permissions and ownership are two of the most important parts of Linux, and a very common cause of problems: a program that cannot read or write a file it needs will fail with errors.
