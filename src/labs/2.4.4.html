About this lab

Log files record events: what happened, when, and often who or what caused it. Analysts read them to troubleshoot problems and to investigate security incidents. In this lab you read web server and operating system logs, track down the logs of a service on an unfamiliar system, and watch logs change in real time.

Objectives

  • Part 1: Log file overview
  • Part 2: Locating log files in unknown systems
  • Part 3: Monitoring log files in real time

This simulation stands in for the Security Workstation virtual machine. You are logged in as analyst; the sudo password is cyberops. The nginx web server is already running, as it would be after the virtual machine starts.

Part 1: Log file overview

Any software can write log files: applications, background services, and the operating system itself. Where a log goes and what it contains is up to the developer, so the software's documentation should describe its logs.

Step 1: A web server log entry

Here is one log entry from the Apache web server:

[Wed Mar 22 11:23:12.207022 2017] [core:error] [pid 3548:tid 4682351596] [client 209.165.200.230] File does not exist: /var/www/apache/htdocs/favicon.ico

It has five main parts:

  • Timestamp: when the event happened. Server clocks must be accurate so events can be matched across systems.
  • Type: the kind of event, here an error.
  • PID: the process (and thread) ID that Apache was using.
  • Client: the IP address of the computer that made the request.
  • Description: what happened.

Based on that log entry, describe what happened.

On Wednesday, March 22, 2017, at 11:23:12 AM, a client at 209.165.200.230 asked for a file named favicon.ico. The file should have been at /var/www/apache/htdocs/favicon.ico, but it did not exist, so Apache logged an error.

  1. Open Terminal from the Applications button. Run cat /var/log/logstash-tutorial.log.

Are these entries still web transactions? Why is their format different from the single Apache entry above?

Yes. The GET requests, client IP addresses, HTTP/1.1, status codes, and browser names show they are web server events. The format differs because this server was configured to record different fields in a different order.

Step 2: An operating system log

Linux stores most log files in /var/log. The messages file records many system events, such as a USB drive being connected, a network card coming up, or repeated failed root logins.

  1. Run sudo more /var/log/messages. sudo is needed because the file belongs to root. On a real system, more shows one page at a time; here it shows the whole file.

Logs are key to troubleshooting. A user reports that all network operations were slow around 4:20 AM on May 19.

Can you find evidence of that in the log? If so, which lines? Explain.

Yes. From May 19 at 04:19:53 to 04:21:27, the kernel logged the network card enp0s3 going down and up again and again (flapping). That confirms the user's report.

Part 2: Locating log files in unknown systems

Analysts often work on computers they did not set up. This part shows a process for finding a service's logs, using nginx as the example.

  1. Start with the documentation. Run man nginx and read the DEBUGGING LOG and FILES sections. The page confirms nginx can write logs and has a configuration file, but the real locations are set when nginx is compiled.
  2. Check that nginx is running: run ps ax | grep nginx.

What does the ps output tell you about how nginx was started?

nginx is running as a master process and a worker process. Its command line shows that its process ID is stored in /run/nginx.pid and that error messages go to stderr (standard error) instead of a file. On this system, the service manager captures stderr in the system journal.

  1. By convention, configuration files are in /etc. Run ls /etc, then ls -l /etc/nginx/.
  2. Run cat /etc/nginx/nginx.conf. Lines that start with # are comments that nginx ignores. The file does not set a log location, so nginx is probably using its defaults.
  3. By convention, logs are in /var/log. Run ls -l /var/log/. There is an nginx folder.
  4. The nginx log folder can be read only by the http user and the log group, so use sudo: run sudo ls -l /var/log/nginx.

The files ending in .gz were made by log rotation. A rotation service compresses the current log, renames it (access.log.1.gz, access.log.2.gz, and so on), and starts an empty log, so no single file grows too large.

Part 3: Monitoring log files in real time

Step 1: The tail command

tail shows the end of a file, by default the last ten lines.

  1. Run sudo tail /var/log/nginx/access.log.
  2. Run sudo tail -n 5 /var/log/nginx/access.log. The -n option sets how many lines to show.
  3. Run sudo tail -f /var/log/nginx/access.log. The -f (follow) option keeps tail running and prints new lines as they are added. There must be a space between -f and the file name.
  4. With tail still running, open Firefox from Applications, go to 127.0.0.1, and choose Reload page a few times. Each request adds a line to the log.
  5. Switch back to the terminal. The new entries are there, and the terminal output is read aloud as they arrive.

What do the new entries tell you, and how do they prove which file nginx uses for its access log?

Each entry shows the client 127.0.0.1, the time, the request (GET / and GET /favicon.ico), the status (200 found, 404 not found), and the browser. They appeared the moment you loaded the page, so /var/log/nginx/access.log is the access log nginx is using.

  1. Press Stop command (Ctrl+C) to stop tail.

Step 2: Bonus tool, journalctl

The Security Workstation is based on Arch Linux, which uses systemd as its init system. The init process is the first process the kernel starts, with process ID 1, and it is the parent of every other process. systemd's logging service, systemd-journald, keeps a journal in binary files. journalctl reads it. Other logging systems, such as rsyslog, can run alongside it.

  1. Run journalctl as analyst, with no sudo.

The hint says you are not seeing all messages. How can you see every entry?

Run it as root: sudo journalctl. Adding the user to the adm, systemd-journal, or wheel group would also work. The -q option hides the hint.

  1. Run sudo journalctl -b to show entries from the current boot.
  2. Run sudo journalctl -b -1 for the previous boot, and sudo journalctl -b -2 for the boot before that.
  3. Run sudo journalctl --list-boots.
  4. Run sudo journalctl --since "2 hours ago", then sudo journalctl --since "1 day ago".
  5. Run sudo journalctl -u nginx.service to see only the entries for nginx. In systemd, services are called units.
  6. Run sudo journalctl -u nginx.service -f to follow nginx entries in real time. Then open Firefox, go to 127.0.0.1, and reload. An error about the missing favicon.ico appears in the terminal. Press Stop command (Ctrl+C) to finish.

Reflection

  • Log files are extremely important for troubleshooting.
  • Log locations follow conventions, but the developer decides. Check the documentation first, then combine web research and investigation of the system.
  • Clocks must be synchronized. If they are not, it is very hard to trace events across systems.
